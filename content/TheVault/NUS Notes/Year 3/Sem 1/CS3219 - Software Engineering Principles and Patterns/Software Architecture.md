# Software Architecture
---
Software architecture is the structure of the system, which comprises of how <b><span style='color:var(--mk-color-yellow)'>data is structured</span></b> & the <b><span style='color:var(--mk-color-yellow)'>externally visible properties of components & their relationships among them</span></b>. 

**In short** software architecture is:
- Overall system organisation
- A high level design of the system

When building an architecture there are **3 main things** to consider:
1) **Components**
They are the elements that are in your software that <b><span style='color:var(--mk-color-yellow)'>models its functionality/responsibility</span></b>. They are essentially anything related to your functional requirements.

This can be like your user service, authentication feature, collaboration service etc.

2) **Connector**
They are elements that <b><span style='color:var(--mk-color-yellow)'>models the interactions between components</span></b> (*transfer data/control/command*).

This can be as simple as a the UI doing a function call to the backend or it can also be through API's.

>[!note] You can view connectors as a way to connect components together

3) **Configuration**
They are just <b><span style='color:var(--mk-color-yellow)'>abstractions</span></b> on <b><span style='color: var(--mk-color-yellow)'>how are you combining</span></b> the components and connectors together. It focuses on the topology or structure.

So **how we bring it all together** is an <b><span style='color:var(--mk-color-turquoise)'>architecture framework</span></b>.

>[!important] Architectures evolve based on computing needs, NFRs and quality attributes

>[!question] So is there a baseline architecture?
>Yes there are and these are called <b><span style='color: var(--mk-color-turquoise)'>reference architectures</span></b>. They are <b><span style='color: var(--mk-color-yellow)'>abstract</span></b>, so a developer can use this and customise based on their needs.
## Architecture Patterns

When developing **many types of software**, though the purpose differs but the <b><span style='color:var(--mk-color-yellow)'>frameworks are roughly the same</span></b>.

>[!note] We are essentially taking a framework and giving it some context to create our application

So these structures are the same for similar applications will lead us to have <b><span style='color:var(--mk-color-turquoise)'>architectural patterns</span></b>.

It is an architecture solutions which forms the <b><span style='color:var(--mk-color-yellow)'>basis of a design</span></b> where it address the problem with a specific context.

>[!warning] Architecture patterns adheres to a set of limitations & constraints

# Architecture Design Decisions
---
When deciding on the design choices there are a lot of **things to consider**:
- Deployment strategy
- What is the best to meet the stakeholders expectations
- Are there existing generic architecture to act as a template
- Single/multi core, Single/multi processor, Stand-alone/distributed?

But how are we going to decide how are we going to divide into smaller components?
## Control Flow

Here we decide on which component <b><span style='color:var(--mk-color-yellow)'>takes control when a certain event happens</span></b>. For instance redirecting the user to another page upon pressing a button.

It gives a <b><span style='color:var(--mk-color-yellow)'>reasoning on the computation ordering</span></b> as well for instance only after computation is finish then the other component can start.

>[!note] Control flow we are focus on how control moves throughout execution
>Data may accompany control (*sometimes no data is passed*).
## Data Flow

Data flow on the other hand focuses of data movement between components. It <b><span style='color:var(--mk-color-yellow)'>reasons on data availability transformation & latency</span></b>.

Either the components requires data generated by another component or it requires data after computation of another component.

>[!note] It is linked with control flow
>As **data moves** through a collection of computations, <b><span style='color:var(--mk-color-yellow)'>control is activated</span></b>.

>[!important] Differentiate control and data flow
>Use different arrows or lines to distinguish between the 2.
## Call & Return

Here is an extension to control flow where we focus on the movement of control from <b><span style='color:var(--mk-color-yellow)'>one component to another and back</span></b>.

It can be either:
- **Hierarchical** (*Can only pass control to components that are below 1 tier*)
- **Non-hierarchical** (*Can pass control to any component*)
## Message & Event

This is how <b><span style='color:var(--mk-color-yellow)'>components interact with one another</span></b>. It can be via events, message passing, RPC & other protocols.

Message passing can be [[Inter-Process Communication#Message Passing|synchronous or asynchronous]]& it is point to point.

>[!abstract] Mechanisms for message passing
>There are 2 mechanisms which we can use:
>1) **Push** - Data is sent to the middleware which will be sent to the rest of the components
>2) **Pull** - Data will be sent to the middleware which the client can request the data to be sent to it
>   
> As a side note a pull is better if there is a a lot of people to send data to (*practicality*).
### Message

Just like in real-life when you send a message it is for some intended person.

Thus, message driven systems has a <b><span style='color:var(--mk-color-yellow)'>unique address for other components to send messages</span></b>.

Then the recipient will waits for the message and react accordingly.
### Events

They are different where some data is emitted and <b><span style='color:var(--mk-color-yellow)'>components which are listening can consume it</span></b>. This usually happens when a state changes.

Unlike messages, components can <b><span style='color:var(--mk-color-yellow)'>choose to act</span></b> on these events or not.

Events are:
- **Immutable** (*Cannot be changed or deleted*)
- **Ordered In** the sequence of their creation

>[!info] Events can be sent to a publishing infrastructure where consumers may later retrieve it
# Modularity 
---
>[!question] Recall that an architecture is a high level design, so how do we break this up into components?
>
>There are a few guidelines:
>- Divide & conquer (*most basic guideline*)
>- Keep a high level of abstraction
>- Increase cohesion (*Put everything related together*)
>- Reduce coupling
>- Design for reuse & reuse design
>- Design for flexibility
>- etc (*Testability, defensive design, portability*)

This is where modularity comes in, it <b><span style='color:var(--mk-color-yellow)'>decomposes a big-chunk into smaller chunks with well-defined interfaces</span></b> or APIs (*for communication*) & it can prevent spaghetti code.

The simplest way of decomposing the software is either by:
- **Layers** (*Horizontal slicing*)
- **Feature** (*Vertical slicing*)
- Or a combination of both

>[!note] Then after decomposing you want to put your components together and that is packaging
>
>So to do all this you will use some [[Design Principles|design principles]], for instance:
>- Program to interface (*components communicate with the same mechanism*)
>- Single responsibility principle
>- Separation of concerns

Modularisation is a <b><span style='color:var(--mk-color-green)'>good way of managing complexity</span></b> by breaking it down into smaller manageable modules then allocate different functions to modules & specify the APIs for interactions.

>[!success] Shorter development time

>[!success] Better flexibility

>[!success] Better comprehensibility
# Architecture Styles
---
There is no 1 style for every software, thus the <b><span style='color:var(--mk-color-yellow)'>difference in style are for different purposes and philosophies</span></b>.
## Categorisation

We can **categorise by our design choices** which can tell us what style to use.
### How is the Code Divided
#### Technical Partitioning

It focuses on **separation of concerns** where the code is <b><span style='color:var(--mk-color-yellow)'>divided based on functionalities, the team formation or the technologies used</span></b>.

>[!example] Example of dividing by team expertise
>We can divide the system by:
>- Presentation (*Frontend*)
>- Services (*Backend*)
>- Persistence (*Database administrators*)
#### Domain Partitioning

This is more <b><span style='color:var(--mk-color-yellow)'>inline with the business concerns</span></b> (*domain*) as it divides it based on the problem. Then each of this partitions can have its own vertical stack (*UI, backend, DB*).

Each domain will have its own <b><span style='color:var(--mk-color-turquoise)'>bounded context</span></b>, which can be thought of as its <b><span style='color:var(--mk-color-yellow)'>role, components and what it is supposed to do</span></b>.

>[!success] Good with small teams
>As we don't have specialised developers but many all rounders. 

>[!example] Example of dividing by domain
>If we have a e-commerce website, we can divide it up like so, each handles:
>- Customers
>- Payment
>- Shipping

>[!note] A combination of both domain & technical can be used
### How is it Deployed
#### Monolithic

>[!info] Also known as single deployed unit

Here we <b><span style='color:var(--mk-color-yellow)'>package all the logical components into 1 big application</span></b> which will run as 1 process.
#### Distributed

All the components are now <b><span style='color:var(--mk-color-yellow)'>independent</span></b> of one another. Each components <b><span style='color:var(--mk-color-yellow)'>runs its own process</span></b> and they <b><span style='color:var(--mk-color-yellow)'>communicate over the network</span></b>, thus this forms the whole application.

## Types of Architecture Styles
### Layer Architecture

This is also known as [[Modeling and Software Architecture#Layered Architecture|n-tiered]] layered architecture. We are <b><span style='color:var(--mk-color-yellow)'>partitioning the application into multiple layers of components</span></b>, each with their own distinct and specific responsibility.

>[!tldr] Essentially the lower layers will provide services for the upper layers

The layered design can be either **closed** or **open**, it just denotes the strictness of communication between layers.

>[!info] Closed Layered Design
>It is **strict** where <b><span style='color:var(--mk-color-red)'>no layer can bridge over</span></b> to layers not directly below it.

>[!info] Open Layered Design
>It is **less strict** where <b><span style='color:var(--mk-color-green)'>layers can bridge over</span></b> to layers not directly below it, but it <b><span style='color:var(--mk-color-red)'>can affect modifiability</span></b>.

>[!success] Supports independent development

>[!success] Allows evolution of different system parts
>This depends on how you packaged the application code and the other components only need to know the interface to communicate.
### Pipe & Filter

In a [[Modeling and Software Architecture#Pipe-and-Filter Architecture|pipe & filter]] pattern, data enters the system and flows through the components one at a time until it reaches its **final destination** known as the <b><span style='color:var(--mk-color-turquoise)'>data sink</span></b> (*it is like a stream of data*).

It uses **pipes**, to <b><span style='color:var(--mk-color-yellow)'>transfer data</span></b> from 1 filter to another, while **filters** just does some <b><span style='color:var(--mk-color-yellow)'>computation or transformation</span></b> to the data.

Filters, **computes incrementally**, meaning <b><span style='color:var(--mk-color-yellow)'>it outputs first</span></b> before taking in another input.

>[!important] Data format should be uniform to the next filter
>When passing data from 1 filter to another, it must follow the input data structure of the next filter.

To **design** a pipe & filter architecture, take a tasks and <b><span style='color:var(--mk-color-yellow)'>divided it into self-contained steps</span></b>, the connect these steps to a data processing pipeline via <b><span style='color:var(--mk-color-yellow)'>intermediate data buffers</span></b>.

>[!success] Filters are independent from one another as they share no state
>This it makes it easily modifiable.

>[!success] Good for applications with limited user interaction
>For instance batch processing systems

>[!example] Example using Azure Functions
>The domain is:**Image processing**
>
>Our **pipe** can be the Azure storage queue
>
>The **filter** can use azure functions like:
>- Content moderation
>- Resizing
>- Reorientation
>- Watermarking
>- Content delivery network (*CDN*) publication
### Model, View, Controller

![[Images/CS3219 Images/MVC Example.png|center|400]]

In this architecture the code is comprise of **3 separate components**:
1) **View** - Anything related to UI
2) **Controller** - Coordinate between model & view
3) **Model** - Represents the business logic (*Mostly your data or the state of the system*)

This architecture is <b><span style='color:var(--mk-color-yellow)'>applicable to programs with GUI</span></b>.

There are some configurations to MVC, for instance:
- The **view & controller can be played by the same object** is they are very tightly coupled
- Inputs can go through the view

>[!note] The goal of MVC is to support user's mental model of relevant information

There are **frameworks which provides an MVC solution** (*templating engine*) just by specifying the behavior.

>[!success] Separation of concerns
>Better <b><span style='color: var(--mk-color-green)'>modularity</span></b>. Since there is separations between, data storage, handling, visualisation & user interaction

>[!success] Facilitates extensibility
>New functionality can be added independently or a new view/controller can be added for a new interface medium.

>[!success] Reduce complexity & side effects
>There is restricted communication between the 3 components

>[!success] Better testability
>It is easier to mock the components
#### Variants of MVC

##### Web MVC

>[!info] The traditional MVC is a monolithic application

In web applications there are **2 communicating entities**:
1) **Server** - Holds the model (*data*)
2) **Client** - The one interacting with the server (*performs the request*)

So how can we **translate this into an MVC**, lets look at it component by component.

1) **Controller**
Mainly responsible for <b><span style='color:var(--mk-color-yellow)'>handling user HTTP request</span></b>, select the model & prepare the view.

Not only that but it has to <b><span style='color:var(--mk-color-yellow)'>map to the correct handler</span></b> based on the request. With this usually the controller can be spilt as:
- A **page controller**, which handles request for a specific page
- A **front controller** which handles HTTP requests (*sometimes the middleware can play this role as a handler*)

>[!info] Handler
>Manages the request and then select the model & prepare the view

2) **View**
<b><span style='color:var(--mk-color-yellow)'>Renders the HTTP response</span></b>. There is also templates which it can use to render contents of the model (*obtain as a HTTP response*).

>[!example] Example of a template
>In ASP.net, views are defined as ASP files which are HTML templates with server side scripts that can generate dynamic content

3) **Model**
It is for the <b><span style='color:var(--mk-color-yellow)'>business logic + persistence</span></b> (*database*). The model can <b><span style='color:var(--mk-color-yellow)'>directly use the database</span></b> or via ORM (*object relational mapping*).

>[!warning] The model has to manage concurrent modifications due to possible same time requests

>[!failure] Here the server does a lot of work
##### SPA

In the traditional static website, the client will communicate via `GET` and `POST` API calls, which was <b><span style='color:var(--mk-color-red)'>not efficient</span></b> since it requires **page refreshes** & the **server does a lot of work**.

This is where SPA comes in which is known as <b><span style='color:var(--mk-color-turquoise)'>single page applications</span></b>.

When the HTML is returned form the server (*only fetches once*), it <b><span style='color:var(--mk-color-yellow)'>also returns an additional program</span></b> (*some JavaScript*), so now we <b><span style='color:var(--mk-color-green)'>don't need to make a new page request</span></b>, only data which is handled by an <b><span style='color:var(--mk-color-turquoise)'>ajax request</span></b> (*asynchronous JavaScript and XML*).

And now the <b><span style='color:var(--mk-color-yellow)'>work is all done on the client side</span></b>.

>[!success] Fluid experience

>[!success] Save bandwidth
>
>You only send over necessary data and not everything else.

>[!success] Reduce the perceived latency
>When the data is about to run our, ajax will request more data so it does not "wait" for the data. It basically pre-fetches data which will be used later on.

>[!failure] Here the client does all the work

>[!fail] Harder to develop

>[!fail] Needs JavaScript
>If JavaScript is not allowed in some companies then this will not be viable.

>[!fail] Vulnerable to XSS
>Cross-site scripting is <b><span style='color:var(--mk-color-red)'>injecting malicious code</span></b> into website. Thus the ajax request can return malicious code.
### Representational state transfer

Representational state transfer also known as **REST**, an architectural style <b><span style='color:var(--mk-color-yellow)'>for distributed hypermedia systems</span></b>.

REST focuses on <b><span style='color:var(--mk-color-green)'>improving</span></b> the following:
- **Performance & scalability** - Statelessness
- **Simplicity of interaction** - Has a fixed set of functions (`GET`, `POST`, `DELETE`) to interact with (<b><span style='color:var(--mk-color-green)'>uniform interoperability</span></b>)
- **Modifiability** - Client & server are separate, connected by the API
- **Reliability**

In REST, it <b><span style='color:var(--mk-color-red)'>defines constrains</span></b> (*set of rules*) for **transferring, accessing & manipulating textual data representations** (*hypermedia*) in a <b><span style='color: var(--mk-color-yellow)'>stateless manner</span></b> across a network of systems.

>[!quote] Hypertext, multimedia, hypermedia
>1) **Hypertext** - Text displayed with hyperlinks to other texts which the reads can immediately access (*low bandwidth & REST was not design for this*)
>2) **Multimedia** - Multiple forms of media (*images, audio, video*) which can be presented with text
>3) **Hypermedia** - Nonlinear medium of information that includes multimedia & links (*high bandwidth*)

>[!success] Systems are less tightly coupled
>Separation of concerns

>[!success] Provides scalability, usability, accessibility & mashup-ability
>**Mashup-ability**: You can put a lot of components together because its loosely coupled.
>
>Because everything is <b><span style='color: var(--mk-color-green)'>self contained</span></b> and we can utility the client through [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Software Architecture.md#Code-On-Demand|code-on-demand]]

>[!fail] Decrease network performance
>Bring stateless means <b><span style='color:var(--mk-color-red)'>increasing the repetitive data sent</span></b> in queries.

>[!fail] Using uniform resource identifier (URI) may degrade efficiency
>Information is <b><span style='color:var(--mk-color-red)'>transferred in a standardized form</span></b> rather than one which is specific to an application needs.
>
>Thus the application might need to spend more time to transform or pre-process the data.
#### REST Constraints

>[!warning] If any of the constraints is violated then we just have a HTTP API rather than a RESTful API
##### Client Server

REST application should have a <b><span style='color:var(--mk-color-yellow)'>client-server architecture</span></b>.

![[Client Server Architecture.png|center]]

They **communicate** with each other using an interface called an <b><span style='color:var(--mk-color-yellow)'>API</span></b>.

>[!question] Why client-server architecture
>The reason is to achieve <b><span style='color:var(--mk-color-green)'>separation of concerns</span></b>.
>
>The client (*frontend*) is not connected with the resources while the server (*backend*) is not connected to the UI or user state.

>[!success] Improve portability of UI

>[!success] Improve scalability of server components

>[!success] Front & back-end can be developed independently
>Decoupling helps independently evolve to <b><span style='color:var(--mk-color-yellow)'>support internet-scale requirements</span></b>.
##### Stateless

If something is stateless it means that it <b><span style='color:var(--mk-color-yellow)'>does not need to retain information about previous requests</span></b>. This means that <b><span style='color:var(--mk-color-yellow)'>each transaction is treated independently</span></b>.

>[!info] Self-contained
> **Queries** in a REST API should be <b><span style='color:var(--mk-color-yellow)'>complete</span></b> meaning the query itself must contain **all the data** needed to do the computation (*as a prarms, headers or in URL*).

>[!important] No client or session state must be maintained in the server

Because of this the server is **bounded** by the <b><span style='color:var(--mk-color-yellow)'>number of concurrent requests</span></b> not the number of clients interacting with it. This is because if we have all the information we can <b><span style='color:var(--mk-color-yellow)'>spawn in a thread which will handle that query</span></b> (*cleaning up is also easier*).

>[!success] Scalable
>All the server needs to do is to clean up the thread resources to serve additional requests.

>[!success] Reliable
>They can recover from partial failures quickly (*some components in the whole system is not working*). Since it does not need to get any previous state.

>[!success] Monitoring
>Monitor the requests sent to analyse but also the results can be used to <b><span style='color:var(--mk-color-green)'>improve scalability & reliability</span></b>.
##### Cacheable

![[Caching in REST Apps.png|center]]

A [[Caching|cache]] is a piece of hardware which **stores data which can be retrieved very quickly**. The idea is that similar requests can just <b><span style='color:var(--mk-color-green)'>pull data from the cache which is much faster</span></b> than from the server.

**Data from the server** should also include a <b><span style='color:var(--mk-color-yellow)'>flag to indicate is it cacheable and for how long</span></b>.
- If its caching on the **backend**, then we need to indicate how long
- If its caching on the **frontend**, then we can use a session token

>[!success] Improved network efficiency
>Caching allows <b><span style='color:var(--mk-color-yellow)'>less interaction with the server</span></b> if possible thus it <b><span style='color:var(--mk-color-green)'>improves efficiency</span></b> and also the user's perceived latency is reduced (*just an illusion*).

>[!failure] Cache can store stale data
>This only happens if we <b><span style='color:var(--mk-color-red)'>do not set when to clear the data</span></b> from the cache.
##### Layered System

The application must be organised as a <b><span style='color:var(--mk-color-yellow)'>layered system</span></b> (*network*). This means that **each layer** <b><span style='color:var(--mk-color-red)'>cannot see</span></b> (*communicate*) <b><span style='color:var(--mk-color-red)'>beyond it's immediate neighbour</span></b>.

Since it can only see its neighbors it is sort of like a pipe & filter where we can do some <b><span style='color:var(--mk-color-yellow)'>data transformation & filtering</span></b> as we pass it on.

>[!success] Improve system complexity
>By restricting complexity and communication to individual layers.

>[!success] Improve system availability & performance
>This can be <b><span style='color:var(--mk-color-yellow)'>achieved by intermediary servers</span></b>. For instance by enabling load-balancing or caching.
##### Uniform Interface

There should a <b><span style='color:var(--mk-color-yellow)'>uniform way of interacting with a server</span></b>, regardless of the device or the type of application. And this should be efficient for large-grained hypermedia data transfer

>[!note]  It exploits HTTP/HTTPS requests & responses to make the interface uniform
>
>It uses standard requests like `GET`, `PUT`, `POST`, `DELETE` & responses like 200 (*ok*), 404 (*not found*).

It follows the <b><span style='color:var(--mk-color-turquoise)'>generality to the component interface</span></b> principle:
- Implementations are <b><span style='color:var(--mk-color-yellow)'>decoupled</span></b> from the services they provide
- System is <b><span style='color:var(--mk-color-yellow)'>free</span></b> from **unnatural restrictions & limitations**

**Any data** that can be sent through this interface is known as a <b><span style='color:var(--mk-color-turquoise)'>resource</span></b> (*resource based*). Recourses are identified using a <b><span style='color:var(--mk-color-turquoise)'>resource identifiers</span></b> (*Unified-RI*) which **maps to some set of entities**.

>[!example] Example of resource identifiers
> If our query is `/User/123` it means it is referring to user with and ID of 123.
> 

>[!abstract] Resource archetypes
>1) **Document** - It represents a specific document / record / instance (`/products/{prodice-id}`)
>2) **Collection** - It represents a list or director of documents (`/products`)
>3) **Store** - Similar to a collection but what is added / deleted etc is handled by the user (`/shop/{user-id}/cart`)
>4) **Controller** - Executable methods with inputs & outputs not under CRUD methods (`POST /alerts/123456/resent`, here `resend` is the name of the controller)

The **server** or components can understand by inspecting & <b><span style='color:var(--mk-color-yellow)'>perform on operations on resource representation</span></b>.

>[!info] Representation
>It is just a combination of data and the metadata.

When a client makes a request they <b><span style='color:var(--mk-color-yellow)'>will have a representation of the resource & the information</span></b> to modify the resource on the server.

>[!example] Example of a interface call
>`HTTP DELETE /device-management/managed-devices/{device-id}`. Here the user will know what device ID the device they want to delete.

**This call should be self-describing**, which means that the **message** being passed to the server <b><span style='color:var(--mk-color-yellow)'>must include enough information & is easy to analyse</span></b> the request to be executed.

>[!info] Hypermedia Driving Application State
><b><span style='color:var(--mk-color-yellow)'>Representations that are exchanged should be linked</span></b>.
>
>Clients that need the resource can discover them and obtain them from the links. These links enable exposing new resources and application state transitions.
##### Code-On-Demand
Instead of extending functionality on the server side, we can just let it <b><span style='color:var(--mk-color-yellow)'>download executable code from the server</span></b> (*applets or JavaScript code*).

>[!question] How does it work?
>When the client sends a request, the <b><span style='color:var(--mk-color-yellow)'>server will send back the code which the client will execute</span></b> to achieve what it needs to do.
>
>For example, maybe the server will send all the data and send code to filter the data to be executed in the frontend.

>[!success] Allows extensibility
> This simplifies the client from having to pre-implement all the functionality.

>[!failure] If the browser blocks JavaScript and applets then none of this will work
>That why **this is optional** and not mandated by REST.
### Modular Monoliths

A [[Modeling and Software Architecture#Monoliths|monolith]] is a single deployable unit so <b><span style='color:var(--mk-color-yellow)'>all components and functionalities are built in it</span></b>.

>[!abstract] Advantages & disadvantages of a monolith (not modular)
>**Advantages**
>- Easy to deploy
>- Simplicity of application evolution
>- Better performance, as applications do not need to communicate through the network
>- Testing is easier as components are bundled into 1
>  
>  **Disadvantages**
>- High coupling since everything is in 1 big application
>- Testing becomes harder as regression bugs can no exist throughout the whole system instead of a small part
>- Slower development as it grows. This is due to complexity and coupling
>- Any small change we need to redeploy the whole application

Now when we talk about **modular monoliths**, we are essentially breaking the functionality which was supposed to all be in 1 unit into <b><span style='color:var(--mk-color-yellow)'>seperate units by business concerns</span></b> (*domain*).

**Example of a modular monolith**:
![[Example of a Modular Monolith.png|center]]

>[!info] Within each domain we can also separate by technical concerns

>[!success] It reduces coupling
>
><b><span style='color:var(--mk-color-yellow)'>Each domain is independent</span></b> of one another but interact through APIs.

>[!success] Domain partitioning
>Better aligned with the business problem & we can build <b><span style='color:var(--mk-color-yellow)'>cross-functional teams that specialise in domains</span></b>.

>[!success] Maintainability
>Since each part of the application is separated by domain, is it easier to maintain.

>[!success] Testability
>Since we can partition **teams by domain**, they will have a <b><span style='color:var(--mk-color-green)'>better understanding</span></b> & thus will come up with better test cases (*edge cases or scenarios*).

>[!fail] Hard to reuse
> Hard to reuse components since it is <b><span style='color:var(--mk-color-red)'>tailored to the domain</span></b> (*domain-level dependent*).

>[!fail] Fragile boundaries
>Functionalities may be developed to accidentally spawn across modules (*duplication*).
>
>This functionality might be important for this domain but it breaks the boundaries.
# Architecture Diagrams
---
They are <b><span style='color: var(--mk-color-yellow)'>free form diagrams</span></b> which shows the <b><span style='color: var(--mk-color-yellow)'>big picture</span></b> of what is bring build. 

It mainly focuses on the [[Year 2/Sem 2/CS3213 - Foundations of Software Engineering/Modeling and Software Architecture.md#C4|4 Cs]] (*context, container, component, code*) and it acts as a map for developers to navigate the source code or communicate with others.

But when making architecture diagrams follow the following standards:
- **Consistent notation**: Consistent notation and symbols
- **Do not make it ambiguous**, make it clear and understandable, indicate the arrows are they control or data flow
- **Do not use general terms** and identity, make it specific to the context of your system
- Balance between **too much and too little** detail
