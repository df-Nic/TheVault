# Events
---
An **event** is a construct that is used to <b><span style='color: #F0E68C'>record or indicate that something happen in the system</span></b> (*within the business system*).

>[!info] Ubiquitous language
>It is a <b><span style='color: #F0E68C'>common language</span></b> during the development of services that is similar in both the solution and the problem.

These **events can act** as both <b><span style='color: #F0E68C'>data</span></b> and as a <b><span style='color: #F0E68C'>means of asynchronous communication</span></b> between services,

Events should be <b><span style='color: #F0E68C'>immutable</span></b>.

>[!note] So these events can act as a notification to the rest of the system

To generate a event is <b><span style='color: #F0E68C'>originates from the end user</span></b>, this is known as a <b><span style='color: #B0E0E6'>initiating event</span></b> which typically starts some business process.

Then afterwards any other internal <b><span style='color: #F0E68C'>events generated by the service due to the initiating event</span></b> is called a <b><span style='color: #B0E0E6'>derived event</span></b>. **These events happen more than initiating event**.

**Derived events are important** to ensure that the <b><span style='color: #F0E68C'>business process is completed</span></b>.

>[!tldr] Putting it all together
>
>When a initiating event happens, the components will respond to it and then broadcast what it did to the rest of the system (*derived event*). 
## Structure of an Event

**Events can be lightweight depending on what we want to store** in them. But most of the time they <b><span style='color: #F0E68C'>follow the key value format</span></b>.

>[!info] Key-value format
>The **key**, is used for identification, routing and also doing operations based on the key.
>
>The **value** is the details related to the key.

But typically events will <b><span style='color: #F0E68C'>store some info</span></b> which is required by the service to retrieve the rest or <b><span style='color: #F0E68C'>provide everything</span></b>.

>[!success] It is typically better to provide all the information
>It <b><span style='color: #98FB98'>achieves separation of concerns</span></b> and <b><span style='color: #98FB98'>reduce coupling</span></b>, <b><span style='color: #98FB98'>single responsibility</span></b> and <b><span style='color: #98FB98'>better cohesion</span></b>.
>
>Also if you look on a border scale it is <b><span style='color: #98FB98'>plug and play</span></b> since it <b><span style='color: #F0E68C'>does not rely on fetching data from other sources</span></b>.

But there are a few types;
1) **Unkeyed**
It just <b><span style='color: #F0E68C'>describes an event as a singular fact</span></b>, there is no keys just the value

>[!example] Item ID 5 has been clicked at 12PM

2) **Entity**
It <b><span style='color: #F0E68C'>describes some properties and state of the entity</span></b>. This entity has a <b><span style='color: #F0E68C'>unique value</span></b> and that is its key

>[!example] User = {userID: 1, Name: Jane, Age:23}
>
>Other than `userID` the rest are values for this user entity.

3) **Keyed**
It is mostly <b><span style='color: #F0E68C'>used in a stream of events to ensure data locality</span></b> within a partition. Here the **key** does not correspond to an entity but is <b><span style='color: #F0E68C'>used as a partition</span></b>.

This can be <b><span style='color: #F0E68C'>used as a way to only notify interested listeners</span></b> based on the key.

>[!example] Lets say we have a question service then we can stream the questions into 2 different queues by difficulty
>
>So here the difficulty is the key and the rest of the data are the values.
## Asynchronous Communication

When using events we are trying to achieve a **fire and forget communication**, which is also known as <b><span style='color: #B0E0E6'>synchronous communication</span></b>.

So when a event is broadcasted, it will <b><span style='color: #F0E68C'>not wait for a response nor it care if the components is available</span></b> or not.

>[!note] Synchronous Communication
>
>As mentioned [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Microservices.md#Service Communication|previously]], when a event is sent it will <b><span style='color: #F0E68C'>wait for a response</span></b> before doing anything else.

>[!info] Intermediaries
>As mention in asynchronous communication, events are broadcasted, so what if the <b><span style='color: var(--mk-color-red)'>service is down</span></b>. This is where intermediaries (*Kafka*) is used.
>
>It <b><span style='color: #F0E68C'>acts like a log to store all the events</span></b>, and when the service is back up it will read from the log and execute what it needs to do.

>[!success] Better responsiveness
>The user takes less time to get a response for a request since it <b><span style='color: #98FB98'>does not need to wait for all the other services to finish</span></b> (*this leads to less coupling also*).

>[!success] Better availability
>In a synchronous communication scheme, when a service is down the whole system is down.
>
>Synchronous communication <b><span style='color: #98FB98'>will not bother if the other service is running</span></b>.

>[!failure] More complex application
>
>Handling with asynchronous problem is <b><span style='color: var(--mk-color-red)'>difficult to debug</span></b>.
>
> So how can we do reconciliation, how do we handle errors between all the different services.
# Event-Driven Architecture
---
Or **EDA** is a way of designing and building systems <b><span style='color: #F0E68C'>based on the exchange of events</span></b>.

So it is the <b><span style='color: #F0E68C'>events that drive the system</span></b>:
- Communication through events
- Events triggers certain actions from components to deliver data to some listener

>[!note] It is essentially like a pub/sub system
>
>![[Pub-Sub System Example.png|center]]
>
>A user will initiate an event which our **components** (*consumers*) <b><span style='color: #F0E68C'>subscribe to events of interest</span></b>. Then when a <b><span style='color: #F0E68C'>relevant event happens these consumers will act accordingly</span></b>.

EDA relies on [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Event Driven Architecture.md#Asynchronous Communication|asynchronous communication]] when sending and receiving events, if not then <b><span style='color: var(--mk-color-red)'>each service can only handle one event at a time</span></b> (*blocking*).
## Components in EDA

![[Components in EDA.png|center|300]]

There are **3 key components** (*first class citizens*):
1) Event producers or generators: Publish data onto streams or queues, the ones that <b><span style='color: #F0E68C'>initiate the events</span></b>.
2) Event broker (*event bus*): It is our intermediary, it <b><span style='color: #F0E68C'>stores or logs events until they are processed</span></b> (*usually they are not removed*)
3) Event consumers or listeners: Consume event data, they <b><span style='color: #F0E68C'>act based on events generated</span></b>

>[!success] Producers & consumer are decoupled from each other
>Producers does not know which consumers are listening (*and even other producers*).
>
>Consumers are decoupled from each other & they only see events.
## Differences Between EDA and Microservice Architecture

### Communication

One thing it will differ is **communication method & performance**. In <b><span style='color: #F0E68C'>EDA it must be asynchronous</span></b> (*and driven by events*), while microservices can have both.

So with [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Microservices.md#Service Communication|synchronous communication]] it <b><span style='color: var(--mk-color-red)'>creates latency which slows down the system</span></b>.

### Data Ownership & Bounded Contextd

The other is our [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Microservices.md#Database-Server-Per-Service Pattern|data ownership]] and [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Microservices.md#Bounded Context|bounded contexts]]. In EDA, it is <b><span style='color: #F0E68C'>alright for databases to be shared</span></b> across multiple services (*there is no need for data ownership*). 

>[!question] Why does it not need data ownership?
> Because services <b><span style='color: #F0E68C'>can rely on events to work with shared data</span></b>.
> 
> For example when a service updates it sends an event then the other service will know the data is ready and pick it up.

These <b><span style='color: #F0E68C'>bounded context is a nice to have</span></b>, we do not enforce a particular boundary of a particular service or functionality.
### Events & Requests

In **EDA**, it mainly handles events, it is <b><span style='color: #F0E68C'>built on event processing</span></b>. So the components responds to something that has happen which can in turn trigger more events.

For **microservices** it mainly is <b><span style='color: #F0E68C'>built on request processing</span></b> (*or command*). meaning it will do something when they need to. For instance a component will send a request or command to the other component.

>[!note] Essentially events does not need to know who to process the event while for requests the microservice needs to know who to do this
# Event-Driven Microservices
---
This is a <b><span style='color: #F0E68C'>hybrid architecture</span></b> where it combines microservices and event driven architecture.

To develop this architecture all we need to do is <b><span style='color: #F0E68C'>combine the concepts of both EDA's and microservices</span></b>:
- **Asynchronous communication** (*EDA*)
- **Cohesive service** (*Microservice*) or single responsibility principle
- **Data ownership** (*Microservice*)

>[!important] You do not need to completely eliminate synchronous communication
>
>In this event-driven microservices it is <b><span style='color: #98FB98'>alright to have a combination of both</span></b> synchronous and asynchronous communication.

![[Example of Event-Driven Microservices.png|center|450]]

>[!info] In the sample above each microservice has its own database which was omitted

So we just need to <b><span style='color: #F0E68C'>define our bounded context</span></b> between the components.

Now there components or microservices **communicate asynchronously** through <b><span style='color: #F0E68C'>producing and consuming events</span></b>. These events are usually in a <b><span style='color: #B0E0E6'>event stream</span></b>

>[!note] As a guideline an event stream is owned by 1 microservice 
>
>Meaning that the <b><span style='color: #F0E68C'>events in that stream is all produced by the same microservice</span></b>.
>
>This <b><span style='color: var(--mk-color-red)'>can be violated</span></b> but is a good guideline to follow.

>[!success] Advantages of event-driven microservices
>- **Performance**: Async communication thus it can multitask which is very fast
>- **Scalability**: Services are decoupled and async thus it can be scaled up/down
>- **Maintainability**: Independent from one another, easier to maintain
>- **Evolvability**: Its services trigger on derived events which more functionality can be added
>- **Fault tolerance**: High decoupled, thus no single point of failure

>[!failure] Disadvantages of event-driven microservices
>- **Complexity**: Complex due to async communication & varied DB topologies and their trade-offs
>- **Testability**: Few dependencies thus easy to mock. However high effort to test async processing & independent services
# Event Store / Broker
---
When an event is sent to a receiver, there should be a <b><span style='color: #F0E68C'>middleware to handle all these events</span></b> (*event storage with infinite retention*) before the receiver receives it. So this is done by the <b><span style='color: #B0E0E6'>event store / broker</span></b>.

Also known as a <b><span style='color: #B0E0E6'>event bus</span></b>. Its other purpose is to <b><span style='color: #F0E68C'>receive source data</span></b>, then <b><span style='color: #F0E68C'>publishes it on source specific topics</span></b> (*these are our [[Year 3/Sem 1/CS3219 - Software Engineering Principles and Patterns/Event Driven Architecture.md#Structure of an Event|keyed events]]*).

>[!info] These topics allow listeners to subscribe to topics of interest

It also has a <b><span style='color: #F0E68C'>communication mechanism to send the events</span></b> to the correct people.

Some properties of an event brokers are:
- **Immutable**, the events cannot be edited
- **Append-only**, we can only add events and nothing else

>[!important] There is no undoing an event as an event means something that happen in the application
>However you can have another event to undo what was done in some previous event.

Typically events signifies asynchronous communication but we can also <b><span style='color: #F0E68C'>enforce ordering though an index</span></b> (*queue like behavior*) which the broker maintains.

This leads to <b><span style='color: #B0E0E6'>replayability</span></b> where anyone can use the index to read any event. This provides a <b><span style='color: #F0E68C'>single source of truth</span></b> and is <b><span style='color: #F0E68C'>foundational for communication between microservices</span></b>.

It also supports partitioning (*using topics*) also known as <b><span style='color: #B0E0E6'>sub streams</span></b>, which depends on the application needs.

>[!question] How to ensure only 1 consumer handles the event?
>We can combine the <b><span style='color: #F0E68C'>consumers into groups and elect a leader</span></b> which will maintain the latest event processed.

We can also <b><span style='color: #F0E68C'>apply rate limits</span></b> to producers, consumers & groups.

>[!success] This allows scalability
>Events are managed by the broker and we can churn out more producers or consumers

>[!success] Allow parallelism
>With different partitions, events can be handed in parallel.
